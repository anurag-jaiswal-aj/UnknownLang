# M2.5 Implementation Architecture & Requirement Traceability Review

## Summary

This review examines the M2.5 implementation architecture and requirement traceability for the UnknownLang Wave 2 benchmark. The change establishes a two-layer validation architecture: generator-layer checks for T5, T7, T8, T13 and generic validator-layer checks for T1, T2, T6, T9, T10, with deferred rules T3, T4, T11, T12, T14, T15.

**What changed:** The M2.5 implementation introduces a clean separation between generator-layer validation (T5, T7, T8, T13) and generic validator-layer checks (T1, T2, T6, T9, T10). T13 identifiability enforcement is generator-specific, not generic, avoiding cross-category validation overhead. T6 uses substring matching which has a theoretical false-positive risk.

**Approach taken:** Generator-layer checks prevent invalid tasks at creation; validator-layer checks provide defensive validation for all task records. Deferred rules are marked as not implemented with stub validation rules.

**Watch for:** T6 substring matching has theoretical false-positive risk when hidden tests exist, though M2.5 generators never create hidden tests. T12 leakage lint is deferred despite being mentioned in owner review documentation.

**Verdict**: APPROVED

---

## High-level view

The generator layer enforces T5 two-source verification, T7/T8 pair validation, and T13 identifiability for INF tasks. These checks run during task generation and reject candidates that fail before producing a task record. The generic validator layer enforces T1 schema validation, T2 task ID consistency, T6 public/private disjointness, T9 non-triviality, and T10 chance floor limits. Deferred rules are represented as placeholder validation rules that record the rule name but skip actual checking.

The T13 identifiability check is confined to INF category generation. When generating an INF task, the generator queries all surface operators used in the query, then validates that each operator has exactly one consistent canonical meaning given the public examples. This is implemented in a dedicated `T13Identifiability` class that reuses the execution engine to evaluate candidate canonical operations against example values.

T6 public/private separation uses Python's `in` operator for substring matching between hidden test calls and public examples/query text. This has a theoretical false-positive risk when one expression is a substring of another, but the risk is low because M2.5 generators never create hidden tests (evaluation.tests is always empty), and the check runs on generator-controlled query text where substring overlaps are unlikely in practice.

## T5 two-source verification integration

T5 verification ensures the expected value is confirmed by both the production execution engine and an independent reference evaluator. The verification runs in two places:

1. **Generator layer**: `T5Verification.verify()` is called after task construction in `generate_single_task()`, `generate_pair()`, and `generate_semantic_config_boundary_task()`. The method compares both engines' results against the expected value and returns failure if either differs.

2. **Pair generation**: Both control and treatment tasks undergo T5 verification in the `generate_pair()` method, using the same `T5Verification` instance that shares the environment registry with the generator.

The `T5Verification` class shares its environment registry with the generator, so environments registered during pair generation (via `_mint()`) become available for T5 verification of the treatment task. The verification translates queries back to canonical surface names before running, ensuring both control and treatment use the same canonical semantics even when surface tokens differ.

---

## T7/T8 pair validation

T7 and T8 validation runs in the generator layer during `generate_pair()` and `validate_pair()`. T7 ensures only allowed fields differ between control and treatment based on the variation type, while T8 ensures pairs are discriminating when required.

The validation uses a `_flatten()` helper that extracts nested fields (prompt.* and protocol.*) into a flat dict, then compares values across control and treatment.

- **T7 canonical query consistency under `environment:surface_names`:** The code translates both queries to canonical form and compares, but this only triggers when surface_names is the only variation (not when combined with other variations). If `varies = ("environment:surface_names", "example_policy")`, the canonical check is skipped, which is correct but undocumented.

**The discrimination check** (`_DISCRIMINATING = {"environment:operator_meaning", "environment:semantic_config"}`) only applies when these variations are present. For `environment:surface_names`, the expected value must remain equal (same canonical semantics), which is correct.

## T13 identifiability enforcement

T13 identifiability is enforced ONLY in the generator layer for INF tasks, not in the generic validator. This is by design: T13 requires access to the execution engine and a full language spec to evaluate candidate canonical operations, which is expensive and irrelevant for non-INF categories.

**Implementation details:**

1. **Generator initialization**: When `TaskGenerator.__init__()` receives a registered environment, it creates a `T13Identifiability` instance with the environment's semantic configuration (arithmetic mode, short-circuit behavior).

2. **Query operator extraction**: `query_operators()` parses the query AST, tracks defined function names, and identifies surface operators used in the query (excluding keywords and defined functions).

3. **Example parsing**: `parse_example()` extracts `(op arg1 arg2 ...) = result` patterns, returning operator name, arguments (as literals), and result.

4. **Candidate filtering**: `candidates()` filters canonical operations by:
   - Matching arity
   - Matching argument types (with "any" wildcard support)
   - Matching return type
   - Evaluating each candidate against all examples via the real execution engine
   - Returning only operations that produce exactly the expected results

5. **Final check**: `check(query, examples)` returns `(True, "")` only if every query operator has at least one candidate and no operator is ambiguous (exactly one candidate).

**All INF generation paths apply T13:**
- `generate_single_task(category="INF")` at generator.py lines 392-405
- `generate_pair()` uses standalone tasks (no T13)
- `generate_semantic_config_boundary_task()` returns SYN category (no T13)

**Edge case handling:**
- Unregistered environments fail-closed with clear error message
- Inconsistent arity in examples is rejected
- Contradictory examples (same args, different results) are rejected
- Ambiguous operators (multiple candidates) are rejected

**T13 profile consistency gap:** The identifiability check uses `to_canonical()` for translation but doesn't verify the surface profile in `provenance` matches the environment's. If they differ, canonical mappings may be incorrect. This is unlikely since the generator always stores the profile during INF generation, but it's not validated.

## T6 substring matching false-positive risk

**The implementation** (validation.py lines 157-168):
```python
for test in evaluation.tests:
    if test.visibility == "hidden":
        if test.call in public_examples:  # substring check
            raise ValidationError("T6", f"Hidden test call matches public example: {test.call}")
        if test.call in query_text:  # substring check
            raise ValidationError("T6", f"Hidden test call matches query: {test.call}")
```

**The issue:** Uses Python's `in` operator which performs substring matching:
- Example: `hidden_call = "(add 1 2)"`, `query_text = "(mul 10 (add 1 2))"`
- Result: `hidden_call in query_text` returns `True` even though the expressions are different

**Risk analysis:**

| Factor | Assessment |
|--------|-----------|
| **Theoretical false-positive risk** | confirmed | Substring matching is inherently vulnerable to partial matches |
| **Practical impact in M2.5** | none | Generators never create hidden tests (evaluation.tests is always empty) |
| **Query space properties** | low risk | Generated queries are s-expressions with consistent formatting; partial overlaps are rare |
| **Future-proofing** | medium concern | If hidden tests are added later, this should use AST-based equality |

**Current status:** The T6 check is defensive and will activate if hidden tests are added later. For M2.5, it's unexercised because `evaluation.tests` is always empty.

**Recommendation for future:** If hidden tests are introduced, replace substring matching with AST-based equality comparison using the language grammar.

## Implementation layer mapping

| Layer | Rules | Status |
|-------|-------|--------|
| **Generator** | T5, T7, T8, T13 | ✅ Implemented |
| **Generic validator** | T1, T2, T6, T9, T10 | ✅ Implemented |
| **Deferred** | T3, T4, T11, T12, T14, T15 | Not implemented |

**Generator layer checks:**
- T5: Two-source verification in `T5Verification.verify()` (generator.py)
- T7: Pair canonical projection in `validate_pair()` (generator.py)
- T8: Pair discrimination in `validate_pair()` with `_DISCRIMINATING` set (generator.py)
- T13: Identifiability in `T13Identifiability.check()` (identifiability.py)

**Generic validator checks:**
- T1: Schema version and required fields in `validate_task()` (validation.py)
- T2: Task ID hash consistency via `compute_task_id()` (identity.py)
- T6: Public/private disjointness via substring matching (validation.py)
- T9: Non-triviality via AST-based literal extraction (validation.py)
- T10: Chance floor limit via `_validate_chance_floor()` (validation.py)

**Deferred rules** are represented as placeholder `ValidationRule` objects added to `rules_passed` without actual checking.

## Issues (6)

1. **T6 substring matching false-positive risk** — Hidden test calls may match query text or public examples via substring when they should be structurally distinct. No practical impact in M2.5 since no generators create hidden tests, but if hidden tests are added later, use AST-based equality instead of `in` operator.

2. **T13 profile consistency gap** — The identifiability check doesn't verify the surface profile in `provenance` matches the environment's. If they differ, canonical mappings may be incorrect.

3. **T5 environment registry lifetime dependency** — The shared environment registry relies on the generator maintaining the same dict instance across all generation paths. This works but isn't explicitly documented.

4. **T7 canonical check skips with combined variations** — When `varies = ("environment:surface_names", "example_policy")`, the T7 canonical query consistency check is skipped. This is correct but undocumented.

5. **T12 still deferred** — The `leak_test()` helper in projection.py is a testing utility, not an enforcement gate. T12 is not implemented in M2.5.

6. **T9 regex fallback for literal extraction** — The Lark grammar allows ANY operator name, which is correct for validation but could be improved with the actual language grammar for better robustness against edge cases.
