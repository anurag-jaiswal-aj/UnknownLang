# Security Review: M2.5 Public/Private Data Separation

This review examines the security and data isolation properties of the M2.5 task schema implementation, focusing on public projection, hidden test isolation, provenance handling, and secret/credential prevention.

The `project_public()` function in `src/challenge/projection.py` serves as the primary security boundary. It strips private metadata (expected answers, hidden tests, difficulty, verification evidence, provenance, and notes) from task records before exposing them to models or external systems.

## Summary

The implementation provides robust public/private data separation with several important security properties:

- **Public projection correctly excludes** expected answers, hidden tests, hidden definitions, difficulty, protocol.role, verification, provenance, and notes
- **Hidden tests are properly isolated** via `project_public()` filtering (visibility="hidden" tests removed)
- **Provenance metadata is excluded** from public view by design (not a field in PublicTask)
- **Secret/credential prevention** works at the source-code level: hidden definitions have their source filtered to empty string
- **T6 validation** enforces disjointness between hidden tests and public content (substring matching)
- **T12 leakage lint** (`leak_test()` helper) is a testing utility, not an enforcement gate—this is acceptable per spec since projection already filters private data

The main concern is that **T12 remains deferred**—there is no runtime check to ensure no private data appears in prompts constructed from the public view. This is intentional per the M2.5 spec but should be addressed in future versions.

**Verdict**: SECURITY_VERDICT: PASS with caveats.

## High-level view

The public projection boundary (`project_public()`) effectively isolates hidden test data and private metadata by excluding them from the PublicTask dataclass entirely. Hidden definitions are filtered at the source level—their `source` field becomes empty string when visibility is "hidden", while the metadata structure (visibility flag, must_define) persists.

T6 validation in the generic validator (`src/challenge/validation.py`) checks that hidden test calls don't appear as substrings in public examples or the query. This is a defensive measure with low practical risk since generators don't create hidden tests in M2.5.

Provenance is never part of the public view—`Provenance` is a separate field on `TaskRecord` that isn't included in `PublicTask` at all. This is a solid design decision; provenance is generator metadata, not task content.

The `leak_test()` helper is a testing utility for T12, not an enforcement gate. It verifies that sentinel strings don't appear in public projections, but it's not called during generation or validation. This is acceptable because the projection itself is the primary leak prevention mechanism.

## Public projection boundary

The `project_public()` function implements the security boundary between private task data and the public view. It's implemented in `src/challenge/projection.py` and has two code paths: one for `TaskRecord` objects and one for dictionaries.

**Key exclusion rules** (verified by `tests/test_public_projection.py`):
- Expected answers: Removed entirely (not present in PublicTask)
- Hidden tests: Filtered by visibility field (only visibility="public" tests remain)
- Hidden definitions: Source becomes empty string, must_define cleared
- Protocol.role: Set to None for paired tasks (control/treatment role hidden)
- Difficulty: Not included in PublicTask (per spec section 5.2)
- Verification: Excluded from identity calculation, not present in PublicTask
- Provenance: Not present in PublicTask (genenerator metadata)
- Notes: Not present in PublicTask

The PublicTask dataclass (in `src/challenge/types.py`) only contains:
```python
schema_version, task_id, template, category, protocol, environment_id,
information_condition, prompt, answer_spec, evaluation, input
```

This is a clean, intentional design—the type system itself prevents accidental inclusion of private fields.

### Protocol.role exclusion

For paired tasks (control/treatment), the `protocol.role` field is explicitly set to None in the public projection. This prevents models from learning which environment is control vs. treatment, which would leak information about the semantic variation being tested.

**Code path** (projection.py lines 122-131):
```python
protocol = task.protocol
if protocol.kind == "paired":
    protocol = Protocol(
        kind=protocol.kind,
        pair_group_id=protocol.pair_group_id,
        role=None,  # Explicitly set to None
        varies=protocol.varies,
    )
```

This is correct and tested (`tests/test_public_projection.py` lines 270-285).

## Hidden test isolation (T6)

Hidden tests are isolated via two mechanisms:

1. **Projection filter** (`project_public()` lines 244-248): Only tests with visibility="public" are included in the public evaluation:
```python
public_tests = tuple(t for t in evaluation.tests if t.visibility == "public")
```

2. **T6 validation** (`validation.py` lines 157-168): Runtime check that hidden test calls don't appear in public examples or query text (substring matching).

**T6 validation code**:
```python
for test in evaluation.tests:
    if test.visibility == "hidden":
        if test.call in public_examples:
            raise ValidationError("T6", f"Hidden test call matches public example: {test.call}")
        if test.call in query_text:
            raise ValidationError("T6", f"Hidden test call matches query: {test.call}")
```

### T6 substring matching limitation

The current implementation uses Python's `in` operator for substring matching. This has a theoretical false-positive risk:

- If `hidden_call = "(add 1 2)"` and `query_text = "(mul 10 (add 1 2))"`, the query contains the hidden test as a substring and would fail T6.

**Risk assessment: LOW**

The risk is acceptable for M2.5 because:
1. **Generator never creates hidden tests**: All generation paths return tasks with `evaluation.tests = []`
2. **T6 is defensive**: The validator check exists but is never triggered in practice
3. **Projection filters anyway**: Even if T6 were bypassed, projection removes hidden tests

This is documented in the M2.5_FINAL_OWNER_REVIEW.md section 2 ("T6 Substring-Matching Limitation").

## Provenance handling

Provenance metadata (generator info, version, derivation_seed, surface_profile) is stored on `TaskRecord.provenance` but is **never** part of the public view. There are two reasons:

1. **PublicTask dataclass has no provenance field**: The type system prevents inclusion
2. **Canonical dict excludes provenance**: `to_canonical_dict()` (identity.py lines 126-175) doesn't include provenance in the hashing data

**Provenance structure** (types.py lines 115-119):
```python
@dataclass(frozen=True)
class Provenance:
    """Provenance metadata (PRIVATE - excluded from task_id hash)."""
    generator: str
    version: str
    derivation_seed: str | None = None
```

This is by design—provenance is metadata about how the task was generated, not the task content itself. The public should only see the task (template, prompt, evaluation), not how it was created.

## Secret/credential prevention

Secret and credential prevention works at the definition source level:

1. **Hidden definitions**: Source code is filtered to empty string in projection (`projection.py` lines 24-30):
```python
def _filter_hidden_definitions(source: str, visibility: Visibility) -> str:
    if visibility == "hidden":
        return ""  # Filtered source
    return source
```

2. **Public definitions**: Source code is preserved for model access

3. **must_define field**: Cleared for hidden definitions (must_define becomes None when visibility is "hidden")

This prevents accidental leakage of solution code in hidden input definitions. If a generator creates a hidden definition for a recursive function, the model sees only the public examples and cannot access the actual implementation.

**Test coverage** (`test_public_projection.py` lines 73-108): Verified that hidden definitions produce empty source strings while public definitions are preserved.

## T12 leakage lint (leak_test helper)

The `leak_test()` function (projection.py lines 286-310) is a testing utility for T12 leakage lint, not an enforcement gate. It checks that sentinel strings don't appear in public projections:

```python
def leak_test(task: TaskRecord, sentinel: str = "PRIVATE_SENTINEL") -> bool:
    """Test that private data does not leak into public projection."""
    public = project_public(task)
    public_dict = public.__dict__
    
    def search(obj: Any, path: str = "") -> bool:
        if isinstance(obj, str):
            return sentinel not in obj
        # ... recursive search
        return True
    
    return search(public_dict)
```

**Key point**: This is a test helper, not called during generation or validation. It's used by `tests/test_public_projection.py` to verify no sentinel strings leak into the public view.

**T12 status**: Deferred per spec. The spec says T12 should check that "no hidden test call, hidden definition source or reference solution text appears anywhere in the prompt built from the public view." This requires prompt construction logic, which is not implemented in M2.5. The projection filter is the primary leak prevention mechanism, which is why T12 remains deferred.
