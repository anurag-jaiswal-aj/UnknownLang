# M2.5 Generator Implementation Review

This review examines the M2.5 task generator implementation for correctness and determinism, focusing on core generation paths (EVAL, SYN, INF, CTRL), T5 verification coverage, T7/T8 pair validation, T13 identifiability, T9 non-triviality, and T10 chance-floor validation.

## Summary

The generator implements deterministic task generation from derivation seeds using a `GenerationState` class with seeded hash-based randomness. Four generation paths (EVAL, SYN, INF, CTRL) share common patterns but have significant issues:

1. **T5 verification is missing from SYN generation** — SYN tasks skip T5 verification entirely after generating content and T9 checks, allowing syntactically valid but semantically incorrect tasks to pass.
2. **T9 non-triviality uses inconsistent logic** — `_check_t9_non_trivial` extracts literals with regex, while validation.py uses a Lark-based parser; the two implementations may disagree.
3. **T10 chance-floor validation exists in validation.py but isn't applied in generation** — The generator always sets `chance_floor_ppm=None`, so T10 is never exercised during generation.
4. **T7/T8 validation logic is sound but only applied in `generate_pair`** — The `validate_pair` function correctly checks canonical projection differences and expected value discrimination for semantic changes.

**Verdict**: NEEDS_CHANGES

## High-level view

The generator uses `GenerationState` to provide deterministic randomness seeded from the derivation seed, with a simple linear-congruential-like hash chain. This provides deterministic generation for a given seed, but the determinism breaks when multiple generation attempts are made (e.g., T9 regeneration) because the state position advances without rewinding.

T5 verification is required for single tasks and pairs, but the SYN path returns before calling it. This is a critical gap because SYN tasks can produce queries that evaluate correctly in the local `_evaluate_expression` but may not match the engine's result due to operator semantics differences.

The T9 non-triviality check in `_check_t9_non_trivial` uses a simple regex to find literal tokens, while the validation module uses a Lark-based AST parser. The two may disagree on what constitutes a literal, especially for complex queries.

T7/T8 validation correctly distinguishes between discriminating variations (operator_meaning, semantic_config) that must produce different expected values and non-discriminating variations that must preserve them. The logic is sound but only runs in pair generation.

T13 identifiability is applied only to INF tasks before they return success, using the environment's semantic configuration. This is correct, but unregistered environments fail-closed.

T10 chance-floor validation is implemented in validation.py with strict type checking (rejecting bools, requiring int, bounds 0-100000), but the generator never exercises it by always setting `chance_floor_ppm=None`.

## <details><summary>Details</summary>

### T5 verification missing from SYN generation

The SYN path in `_generate_syn_task` generates a query and computes its expected value using the local `_evaluate_expression` method. After T9 checks, it builds a task record but **never calls T5 verification**.

```python
# SYN generation (line ~480)
def _generate_syn_task(self, ...) -> dict[str, Any]:
    expression = self._generate_expression(difficulty)
    expected_value = self._evaluate_expression(expression)
    # T9 check here
    # ... then build task without T5 verification
```

In contrast, EVAL, INF, and CTRL paths all call T5 verification in `generate_single_task` (line ~326). This inconsistency allows SYN tasks to be generated that may not match the engine's evaluation.

**Confirmed** — SYN tasks skip T5 verification; other categories do not.

### T9 non-triviality implementation mismatch

The generator's `_check_t9_non_trivial` (line ~625) uses regex to extract literals:

```python
query_tokens = set(query.replace("(", " ").replace(")", " ").split())
```

While validation.py uses a Lark-based AST parser with a fallback to regex. This discrepancy means:
- The generator may pass tasks that validation.py would reject
- The generator may reject tasks that validation.py would accept

The Lark parser is more robust, correctly handling nested structures and different formatting.

**Likely** — The regex-based approach will miss some literals in complex queries (e.g., `(add  -3  5)` with extra whitespace).

### T10 chance-floor validation not exercised

T10 validation exists in validation.py with strict type checking:
- Rejects bools (even though bool is subclass of int)
- Requires actual int type
- Bounds: 0 ≤ value ≤ 100000

But in `_build_task_record` (line ~800), the generator always sets:
```python
answer_spec = AnswerSpec(
    type="value",
    kind="int",
    form=None,
    chance_floor_ppm=None,  # Always None
)
```

This means T10 is never exercised during generation. If chance-floor control is intended, it must be configured at generation time.

**Confirmed** — T10 validation is never triggered because `chance_floor_ppm` is always None.

### T7/T8 pair validation logic is correct

The `validate_pair` function (line ~252) correctly implements:

**T7 (canonical projection)**:
- Only fields of listed variation factors may differ
- For `environment:surface_names`, canonical queries/examples must match after translation
- Query text must be identical unless surface_names variation is used

**T8 (discriminating pairs)**:
- Expected must differ when discriminating variations (`environment:operator_meaning`, `environment:semantic_config`) are used
- Expected must be equal for non-discriminating variations

The logic is sound, but only applies during `generate_pair`, not single task generation.

**Confirmed** — The validation logic is correct for paired tasks.

### T13 identifiability applied only to INF tasks

T13 is checked in `generate_single_task` only when `category == "INF"` (line ~314), using the environment's semantic configuration. This is correct behavior:

```python
if category == "INF":
    if self._t13_identifiability is None:
        return GenerationResult(rejection_reason="T13 requires registered environment")
    t13_ok, t13_error = self._t13_identifiability.check(...)
    if not t13_ok:
        return GenerationResult(rejection_reason=f"T13 identifiability failed: {t13_error}")
```

The identifiability module correctly:
- Parses surface operators from query
- Extracts examples and checks they uniquely identify canonical operations
- Rejects tasks where operators are ambiguous or examples contradict

**Confirmed** — T13 is correctly applied only to INF tasks.

### T5 verification is correctly called for other paths

EVAL, INF, and CTRL paths all call T5 verification (line ~326-330 in `generate_single_task`). The verification:
- Runs reference evaluator and production engine with same spec
- Compares both results against expected
- Fails closed if either differs

**Confirmed** — T5 verification works correctly for EVAL, INF, and CTRL.

### Determinism analysis

Determinism is provided by `GenerationState`:

```python
@dataclass
class GenerationState:
    seed: str
    position: int = 0
    
    def _seeded_hash(self) -> str:
        data = f"{self.seed}:{self.position}"
        return hashlib.sha256(data.encode()).hexdigest()
    
    def next_int(self, max_value: int) -> int:
        hash_hex = self._seeded_hash()
        self.position += 1
        # ...
```

For a fixed seed and single generation attempt, results are deterministic. However:

**Issue**: When T9 regeneration is needed, the state advances and is NOT rewound. Each attempt uses different hash positions, so the generated task differs. This means multiple calls with the same seed can yield different tasks if T9 rejection occurs.

**Issue**: INF tasks generate identifying examples via `_identifying_examples`, which draws from a small range with up to 50 tries. If T13 fails, the task is rejected and a new one is drawn with advancing state — again, not deterministic across attempts.

**Likely** — Determinism holds only for successful first-attempt generation. Regeneration breaks determinism because state advances.

## <details><summary>Issues (5)</summary>

1. **T5 verification missing for SYN tasks** — SYN tasks skip T5 verification after generation, allowing tasks that may not match engine evaluation. Add T5 verification before returning success.

2. **T9 non-triviality implementation mismatch** — Generator uses regex; validation.py uses Lark parser. The two may disagree on literal extraction, causing generation/validation inconsistency. Use the Lark parser from validation.py in `_check_t9_non_trivial`.

3. **T10 chance-floor never exercised** — Generator always sets `chance_floor_ppm=None`, so T10 validation is never triggered. If chance-floor control is needed, add it as a generation parameter.

4. **Determinism breaks on regeneration** — `GenerationState` advances on each attempt, so T9 or T13 rejections yield different candidate tasks. For full determinism, either rewind state on failure or generate candidates without advancing state until final success.

5. **T7/T8 validation only in pairs** — Pair validation logic is correct but not used in single task generation. This is expected behavior (T7/T8 are pair rules), but worth noting.

</details>
