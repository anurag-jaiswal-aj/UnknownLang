## 3. Exact M2.6 Objective

**M2.6 — Benchmark Evaluation Harness**

Implement a deterministic evaluation harness that:
- Accepts a validated task, its environment record, and raw model response text
- Extracts the submission (code block or value answer)
- Validates the submission format and size
- Translates surface syntax to canonical syntax
- Executes through the production runtime with limits
- Classifies execution and submission failures
- Compares actual and expected results
- Returns a structured correctness outcome

### Harness Interface

```python

    task: TaskRecord,
    env: EnvironmentRecord,
    response_text: str,
) -> AttemptOutcome:
    """Pure evaluation function with trusted-local execution boundary."""
```

### AttemptOutcome Schema (Corrected)

```python
@dataclass(frozen=True)
class AttemptOutcome:
    outcome: Literal["ok", "fail", "void"]  # Matches experiment-model.md section 3.3
    score: int | None  # 1 for ok, 0 for fail, None for void
    failure_category: str  # From taxonomy
    detail: str  # String refinement
    diagnostics: dict[str, Any]  # Raw diagnostic data
```

**Contract invariants (experiment-model.md section 3.3):**
- `outcome = "ok"` → `score = 1`
- `outcome = "fail"` → `score = 0`
- `outcome = "void"` → `score = None` (no score contribution)

**Failure category → outcome/score mapping:**
| failure_category | outcome | score |
|------------------|---------|-------|
| `"ok"` | `"ok"` | 1 |
| `"harness_fault"`, `"adapter_unavailable"`, `"resource_limit"` | `"void"` | `None` |
| All other categories (`no_response`, `extraction_failed`, `invalid_answer`, etc.) | `"fail"` | 0 |

**Key corrections:**
- Match experiment-model.md section 3.3 exactly: `outcome`, `score`, `failure_category`, `detail`, `diagnostics`
- `score` is the raw attempt score (1/0/None), not aggregate/statistical scoring (M2.8)
- Adapter failures (`adapter_unavailable`) are recorded by the runner as `outcome="void"` with `score=None`

## 8. Environment Validation (Corrected)

### M2.6 Responsibilities

**Validate provided environment:**
- Check `environment_id` format (`env_` + 64-char lowercase hex)
- Verify `identity_core` has required fields
- Check SHA-256 hashes are valid format
- Validate `runtime_semantics_version` matches current runtime

**Do NOT:**
- Resolve environment from persistent storage (placeholder in `EnvironmentManager.resolve_environment()`)
- Perform cross-process environment lookup (deferred to M2.7+)
- Cache or reuse environments (no persistent EnvironmentManager)

### Validation Implementation

```python
def validate_environment_for_task(
    env: EnvironmentRecord,
    expected_id: str,
) -> list[str]:
    """Validate environment for use with a task. Returns list of violations."""
    violations = []
    
    # Check environment_id matches task's expected_id
    if env.environment_id != expected_id:
        violations.append(f"environment_id mismatch: expected {expected_id}, got {env.environment_id}")
    
    # Validate identity_core fields
    try:
        from src.benchmark.environments import validate_identity_fields
        validate_identity_fields(env.to_dict())
    except ValidationError as e:
        violations.append(f"environment identity validation failed: {e}")
    
    return violations
```

## 12. Deterministic Core vs Watchdog Boundary

### Deterministic Logic (Pure)

The following components are deterministic and have no side effects:
- Response extraction
- Submission validation
- Surface-to-canonical translation
- Result comparison
- Failure classification

### Execution Boundary (Trusted-Local)

The subprocess with watchdog has operational side effects but is deterministic:
- subprocess creation and termination
- wall-clock timeout enforcement
- resource limit measurement

**Determinism guarantee:** Same inputs (task, environment, response_text) always produce identical outcomes, even with subprocess execution.

## 13. Output Schema and Scoring Boundary

### M2.6 Outcome Schema

M2.6 provides **correctness data**, not **scoring** (M2.8 handles aggregate/statistical scoring):

```python
@dataclass(frozen=True)
class AttemptOutcome:
    outcome: Literal["ok", "fail", "void"]  # Matches experiment-model.md section 3.3
    score: int | None  # 1 for ok, 0 for fail, None for void
    failure_category: str  # From taxonomy
    detail: str  # String refinement
    diagnostics: dict[str, Any]  # Raw diagnostic data
```

**Adapter failure ownership:**
- The harness (`evaluate(task, env, response_text)`) does not produce `adapter_unavailable`
- The runner/orchestration layer produces `adapter_unavailable` as `outcome="void"` with `score=None`
- The unified attempt representation can record adapter failures but they originate from the runner

### M2.8 Scoring Engine

M2.8 computes aggregate metrics from M2.6 outcomes:
- P1-P4: Primary metrics (category accuracy, held-out accuracy, etc.)
- D1-D12: Diagnostic metrics (syntax validity, execution rate, etc.)
- Bootstrap uncertainty intervals
- Weighted score W

**Separation:** M2.6 provides raw data; M2.8 provides statistical aggregation.

**Root Cause:**
```python
def _extract_expected_value(expected: Any) -> dict[str, Any]:
    if isinstance(expected, dict):
        return expected
    return {"kind": "other", "value": str(expected)}  # BUG: Converts Expected to string
```

When `expected` is an `Expected` dataclass (e.g., `Expected(value={'kind': 'int', 'value': 42})`):
- `isinstance(expected, dict)` returns False
- Falls through to `str(expected)` → `"Expected(value={'kind': 'int', 'value': 42})"`
- Comparison fails: `{'kind': 'int', 'value': 42}` ≠ `"Expected(value={...})"`

**Fix:**
```python
def _extract_expected_value(expected: Any) -> dict[str, Any]:
    """Extract expected value in standard format.
    
    Handles both the Expected dataclass and serialized dict representations.
    """
    # Handle Expected dataclass
    if hasattr(expected, 'value') and isinstance(getattr(expected, 'value', None), dict):
        return expected.value
    
    # Handle serialized dict
    if isinstance(expected, dict):
        if 'kind' not in expected:
            raise ValueError(f"Expected value must have 'kind' field: {expected}")
        return expected
    
    # Invalid format
    raise ValueError(f"Invalid expected value format: {type(expected)} - {expected}")
```

**Verification:**
- Correct answer `ANSWER: 42` now returns `outcome="ok"` with `score=1`
- Expected dict format still supported for backward compatibility
- Invalid formats raise explicit ValueError

**Impact:**
- All value-answer tasks (EVAL, SYN, INF, CTRL) now work correctly
- No regression in existing tests (1,481 passed, 7 warnings, exit code 0)

## 17. Deterministic Core vs Watchdog Boundary

### Deterministic Logic (Pure)

The following components are deterministic and have no side effects:
- Response extraction
- Submission validation
- Surface-to-canonical translation
- Result comparison
- Failure classification

### Execution Boundary (Trusted-Local)

The subprocess with watchdog has operational side effects but is deterministic:
- subprocess creation and termination
- wall-clock timeout enforcement
- resource limit measurement

**Determinism guarantee:** Same inputs (task, environment, response_text) always produce identical outcomes, even with subprocess execution.
