## 1. T13 Architecture Resolution

### Implementation Reality

**T13 identifiability is enforced ONLY in the generator layer**, not in the generic validator. This is by design.

**Evidence:**

1. **Generator-specific enforcement** (`src/benchmark/generators/generator.py` lines 392-405):
```python
# T13 check for INF
if category == "INF":
    if self._t13_identifiability is None:
        return GenerationResult(
            success=False,
            rejection_reason=f"T13 identifiability requires a registered environment. "
            f"Environment '{self.environment_id}' is not in the registry."
        )
    t13_ok, t13_error = self._t13_identifiability.check(
        task.prompt.query or "",
        list(task.prompt.public_examples),
    )
    if not t13_ok:
        return GenerationResult(success=False, rejection_reason=f"T13 identifiability failed: {t13_error}")
```

2. **T13 identifiability module** (`src/benchmark/generators/identifiability.py`):
   - `T13Identifiability` class with `check(query, examples)` method
   - Validates that every surface operator in the query has exactly one consistent canonical meaning
   - Returns `(False, error_message)` for:
     - Missing operator examples
     - Contradictory examples
     - Ambiguous operator meanings
     - No consistent canonical operation

3. **Generic validator does NOT include T13** (`src/challenge/validation.py`):
   - `validate_task()` returns `ValidationRule("T13", "Identifiability (deferred)")` as a placeholder
   - No actual T13 checking is performed in the generic validator

### Architecture Design

| Layer | T13 Implementation | Status |
|-------|-------------------|--------|
| **Generator** | ✅ Active enforcement via `T13Identifiability.check()` | **Implemented** |
| **Generic Validator** | ⚠️ Placeholder only (`"Identifiability (deferred)"`) | **Deferred** |

## 2. T6 Substring-Matching Limitation

### Contract vs Implementation

**T6 Contract** (from specification):
> Hidden tests must be disjoint from public examples and query text.

**Current Implementation** (`src/challenge/validation.py` lines 157-168):
```python
# Check that no hidden test call matches public examples or query
query_text = prompt.query or ""
public_examples = set(prompt.public_examples)

for test in evaluation.tests:
    if test.visibility == "hidden":
        if test.call in public_examples:
            raise ValidationError("T6", f"Hidden test call matches public example: {test.call}")
        if test.call in query_text:
            raise ValidationError("T6", f"Hidden test call matches query: {test.call}")
```

### Substring-Matching False-Positive Risk

**Problem:** Uses `in` operator for substring matching:
- `hidden_call = "(add 1 2)"`
- `query_text = "(mul 10 (add 1 2))"`
- **Result:** False positive (query contains hidden test as substring)

**Risk Level:** Low

**Justification:**
1. **Generator-controlled query space:** The query is generated, not user-provided
2. **No hidden tests in M2.5:** `evaluation.tests` is always empty in current implementation
3. **Intentional design:** T6 is enforced in the validator but not in the generator

### Evidence

1. **Generator never sets `evaluation.tests`:** All generation paths return tasks with `evaluation=Evaluation(method="exact_match", limits={...}, tests=[])`
2. **Validator T6 check is defensive:** Present but never triggered in practice
3. **T6 in projection:** Hidden tests are filtered in `project_public()` anyway

### Corrected Statement

> T6 hidden test disjointness is enforced via substring matching in the validator. This has a theoretical false-positive risk (substring matching) but no practical impact because M2.5 generators do not create hidden tests. T6 enforcement is defensive and will activate if hidden tests are added in future.
